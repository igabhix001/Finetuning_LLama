# Achieving a Production‑Grade AI Astrologer

Building a reliable, accurate AI astrology service requires rigorous engineering, data, and evaluation—beyond just “plugging in” a fine-tuned LLM. Our audit shows the current system uses a vLLM-based Llama model (with SFT and DPO fine‑tuning, and an optional Pinecone RAG) plus a Gradio interface. In practice, however, sample dialogues reveal key failures: **factual errors, hallucinations, poor context use, and robotic tone**. For example, the system incorrectly predicted a range (Mar–Oct 2026) for a past marriage date and ignored “already married” context, instead giving generic astro-logic (Rahu‑Sun periods). It also output a long undifferentiated list of possible careers (“Hospitality, Real Estate, Automobiles, etc.”) citing a “grounding rule,” which feels unnatural. These issues likely stem from **insufficient domain data, weak user-context integration, and over-reliance on generic training**. In contrast, production-grade offerings (e.g. the Chinese astrology startup FateTell【2†L78-L85】【2†L100-L104】 or the Vedika Kundali API) use extensive domain knowledge and achieve very high accuracy and engagement. Vedika, for instance, reports ~95–100% precision on core calculations (e.g. 95.1% for Dasha predictions, 99.98% for chart calculations【25†L95-L103】) and strong user satisfaction (NPS ≈82 vs. ≈28 for generic AI【28†L217-L219】). Below we outline how to close the gap on data, modeling, evaluation, deployment, and safety to reach that level.  

## 1. Technical Audit: Pipeline & Data 

The architecture suggests a strong foundation: chart preprocessor converts natal chart JSON to YAML, a chat UI (Gradio/FastAPI) sends prompts to vLLM, and training uses Domain-Adaptive Pretraining (DAPT), Supervised Fine-Tuning (SFT), then Direct Preference Optimization (DPO). **Potential issues:**  

- **Context and Input Handling:** If user-specific chart data isn’t properly injected into each query prompt, the model will guess generically. Ensure every user question is accompanied by their parsed chart info. (The responses above seem ungrounded to actual birth data.)  
- **Training Data Gaps:** The fine‑tuning data (SFT) and preference pairs (DPO) must cover real astrological Q&A in Hindi/English. If training examples are few or formulaic, the model learns generic scripts (“Grounding rule indicates…”) rather than nuanced reasoning. The “Grounding rule” responses hint at a fallback pattern, not true LLM inference.  
- **Mix of Rules vs. LLM:** The system appears to mix rule-based snippets (“primary marriage significators: Jupiter, Mars…”) with the model’s output. This hybrid can help precision but risks consistency and tone issues. Any rule-based component must be carefully integrated so the style remains natural.  

To summarize, **improve data and prompts**: collect high-quality conversational transcripts (actual astrologer‑client dialogs), encode chart logic as structured data (to retrieve or condition upon), and ensure the model sees many examples of answering timing/career questions with context. 

## 2. Industry Landscape & Benchmarks 

**Specialized astrology AI** is an emerging field. For example, the startup *FateTell* applied LLMs to Chinese astrology, noting that traditional systems (Bazi, Ziwei Doushu) are “structured symbolic systems” now amenable to LLM inference【2†L78-L85】【2†L100-L104】. Production services (like Vedika’s Kundali API) advertise *astronomical* precision (Swiss ephemeris accuracy to ±0.001°) with AI “validation” on top. Their reported metrics emphasize **accuracy and user metrics**: nearly 95–100% on horoscope tasks (Dosha ~98.7%, Dasha ~95.1%【25†L95-L103】) and business metrics like NPS ≈82 (vs ~45 industry avg【26†L122-L128】) and 94% monthly retention【26†L122-L128】. 

Benchmarks for a chatbot include both *factual accuracy* and *user experience*. In practice, measure not just correct date/planet calculations, but also readability, tone, and user satisfaction. Customer Satisfaction (CSAT or NPS) is a common metric in chatbots【26†L122-L128】. A formal evaluation might combine objective tests (e.g. “given birth data, does the model predict the correct Dasha period?”) with human ratings of tone/helpfulness. Industry guides recommend collecting user feedback at key interaction points to gauge helpfulness and trustworthiness【11†L31-L39】. 

## 3. Failure Modes & Root Causes 

From the sample dialogs, we see several root issues:

- **Hallucination / Inaccuracy:** The model *invented* astrological details (e.g. vague “Rahu-Sun Antardasha” answer, incorrect marriage timeframe). LLMs trained on generic text often hallucinate when asked specific future/past predictions. Without a strong grounding, the model just defaults to plausible-sounding but wrong outputs. This is classic LLM behavior when knowledge is missing【23†L213-L217】.  
- **Lack of Context/Memory:** The assistant ignored user context (“already married”) and repeated queries (“when married?”) without continuity. The conversation likely isn’t maintaining memory effectively. A robust system should track session state or re-parse the updated query with existing data.  
- **Unnatural Style:** Answers mix English and Hindi unnaturally and read like a bullet list rather than a human astrologer. This suggests the fine-tuning prompts or preference examples weren’t consistent on tone. Real astrologers (or good persona guidelines) should be sampled.  
- **Overly Broad “Advice Lists”:** The career answer lists many industries with no strong filtering. This suggests either the model is pattern-matching keywords (“Mercury, Mars”) to a static list, or the training data included a canned list. It failed to personalize (e.g. “your chart suggests X”). 

In summary, the model is likely *confidently wrong* or generic. Causes include **inadequate domain-specific data, missing external knowledge, and prompt design flaws**. Industry practice to mitigate these includes using retrieval-augmented generation (RAG) so the model can cite factual references【17†L131-L140】, and rigorous prompt engineering. For example, a RAG pipeline would load classical astrology texts or historical chart interpretations into a vector DB, then retrieve relevant passages for each question. This can drastically reduce hallucination (“hallucination rate” is a known evaluation metric【23†L213-L217】).  

## 4. Data, Rulesets & Evaluation 

To reach “startup level”, invest heavily in data and evaluation:

- **Domain Dataset:** Curate a dataset of astrology Q&A and chart readings. This includes: birth-chart facts (e.g. “born on X date, ascendant Leo”), expert interpretations (timing of marriage, career path analysis), and diverse user queries. You might generate synthetic examples using known ephemeris algorithms (Swiss Ephemeris) to create “gold” answers for testing.  
- **Rules & Knowledge Bases:** Implement core astrological logic deterministically where possible. For instance, planetary period (Dasha) calculations can be coded and results fed as inputs to the LLM. A “knowledge base” of remedies, zodiac traits, etc., can be stored for retrieval (e.g. attach Pinecone vectors for classical shlokas or advisory texts). This hybrid approach (rules + LLM) is common in regulated domains.  
- **Fine-tuning & Pref. Tuning:** Continue supervised fine-tuning (SFT) on the domain corpus, then use DPO or RLHF to align tone and correctness. HuggingFace notes DPO “skips the RL part” and directly optimizes for preferred outputs, making alignment simpler【24†L61-L64】. For DPO data, collect *pairwise preferences*: e.g. have experts (or yourself) rate multiple model outputs or paraphrase as “better/worse”. This will teach the model to prefer accurate, fluent answers.  
- **Evaluation Framework:** Define both automated and human evaluation. Automated metrics could include retrieval accuracy (e.g. does the model mention the right planetary periods?), consistency checks (dates match ephemeris), and typical NLP scores (perplexity, ROUGE on canned tests). Critically, perform *human evaluation* with astrology experts or user surveys. Use scales for correctness, helpfulness, and tone. Track CSAT/NPS over time【26†L122-L128】. You might mirror the Vedika approach: track engagement (session length, return rate) as a proxy for satisfaction.  

In practice, iterate: integrate user feedback in real time. If a user flags an answer as wrong or unsatisfying (as in your 2/10 rating), collect that example for retraining or prompt adjustment.

## 5. Deployment, Monitoring & Safety 

Building production quality also means a robust infrastructure and guardrails:

- **Infrastructure:** Containerize and orchestrate (e.g. Docker/Kubernetes) for reliability. The Gradio+vLLM example shows deploying both inference server and UI in a container【13†L172-L180】. Allocate GPU resources wisely (vLLM can limit GPU usage【13†L172-L180】) and set up autoscaling for traffic spikes. Ensure a high-availability setup (with redundancy) to meet SLAs. The Vedika benchmark cites 99.97% uptime and sub-5s latency at P95【26†L136-L144】, which is a good target.  
- **Logging & Metrics:** Implement thorough logging of queries, latencies, errors, and user feedback. Use this for alerting on anomalies (e.g. sudden drop in response quality or spike in errors). Monitor standard metrics: CPU/GPU utilization, memory, response times (p50/p95). Compare against benchmarks (Vedika’s P50 ~2.14s, P95 ~6.8s【26†L136-L144】).  
- **User Feedback Loop:** Provide an in-app rating or “Was this helpful?” prompt. Collect CSAT/NPS data【26†L122-L128】【28†L217-L218】. Use this to A/B test new model versions or prompt changes. For example, you could trial a different phrasing style or knowledge injection and see if user scores improve.  
- **Guardrails & Safety:** Even though astrology isn’t medical/financial, deploy standard LLM safety: **input sanitization** and **output filtering**. Reject or sanitize malicious/irrelevant inputs (no HTML/JS in prompts, no requests to break rules)【15†L691-L700】. Use output filters to avoid hallucinated personal data or inappropriate advice. For instance, disclaimers (“For entertainment only”) should be injected to avoid liability. Follow OWASP GenAI guidelines to prevent prompt injection or data leaks【15†L698-L707】【15†L671-L680】. Also enforce data privacy: birth chart info is sensitive; ensure it’s not logged or exposed to third parties.  
- **Ongoing Model Ops:** Version your models, track changes. If you find a systematic error (e.g. model always gets Gemini compatibility wrong), you may need to tweak the dataset or incorporate new rules. Scheduled retraining or fine-tuning with fresh user data will keep the model up-to-date.  

Finally, be prepared for continuous improvement. Production-grade AI is not “set and forget.” It requires regular QA and iteration. Collect metrics and feedback, then refine the data/prompt/model cycle. Adopting practices like A/B testing and small rollouts can help validate changes safely. By combining solid domain knowledge (astrology calculations and texts) with LLM flexibility and strict engineering discipline, you can elevate the system to a startup-ready product.
